# 网盘直连播放

服务器带宽较低时，视频中转会成为瓶颈。`PLAYER_MEDIA_DELIVERY=auto`（默认）在完成 TV 认证后优先获取 TV 播放源：

- TV 渐进式视频（MP4/MKV 等）：受站内登录和播放会话权限保护的接口返回 302，浏览器以原生媒体模式直接读取网盘，不强制要求 CORS，不经过应用服务器转发。设备仍需支持对应视频/音频编码。
- TV HLS：客户端通过 `canPlayType('application/vnd.apple.mpegurl')` 检测原生能力，并在准备播放时提交 `nativeHls: true`。服务器为原生 HLS 设备返回受会话保护的直连入口；播放器不启用 CORS，清单与分片直接由原生媒体管线加载。不支持原生 HLS、需要 hls.js 的客户端仍走原有代理。
- 非原生 HLS 设备仅有 TV HLS 时，若账号允许原文件下载，额外提供“原画直连”。此选项不会取代默认兼容画质；原文件的封装、视频和音频编码必须由设备支持。
- TV 认证或接口不可用时，回退原有 Cookie 播放方式，仍然消耗服务器出口带宽。

播放器优先选择直连转码画质，明确手选的传输方式仍可保留；画质按钮区分“直连/中转”和“杜比视界”。直连使用原声，禁用依赖 CORS 的 Web Audio 音效；从已有音效切入直连时重建视频元素，避免静音。直连失败时提供“使用兼容画质（服务器中转）”，不会静默切回大流量代理。3 Mbps 服务器不能保证中转 4K，直连能力也不能保证上游不限速。

原生 HLS 设备优先普通 HLS 转码源，不因历史选择默认回到杜比 MKV。原生 HLS 直连也保留需用户主动选择的中转地址，沿用同一播放会话鉴权；地址刷新会保留客户端能力。原生 HLS 能力仅说明浏览器支持协议，并不保证具体片源、网络或编码一定可播。

已经签发为直连的播放入口会保持“只直连”约束。如果较旧地址刷新后只能获取 Cookie 代理源，返回 `DIRECT_SOURCE_UNAVAILABLE`，不在客户端仍显示“直连”时静默转发大流量；重复请求也保持此约束。显式兼容播放不受该限制。

## 认证与部署

1. 部署包含此改动的前后端，重启应用容器；不需要清空或迁移片库。
2. 管理员进入“我的 → 播放与片库 → 网盘直连”，查看认证服务地址，点击“同意并生成二维码”，用夸克 App 扫码确认。
3. Cookie 继续用于片库、检索转存及兼容播放。TV 认证是附加认证，不删除原有 Cookie。
4. 默认令牌交换服务为 `https://api.extscreen.com/quarkdrive/token`，会接收授权码和后续刷新令牌；可以用 `TV_TOKEN_EXCHANGE_URL` 指向兼容的 HTTPS 服务。令牌加密存放在部署实例的 `data/` 中，不返回前端。
5. 本地扫码不会自动同步到线上服务器。应在目标部署重新扫码，不要复制或提交明文令牌。

页面必须使用 `Referrer-Policy: no-referrer`，并保留 HTML 中的同名 meta 配置。实测只给 302 响应设置该策略仍不够，浏览器后续 Range 请求可能带上站点 Referer 而被夸克拒绝。反向代理不要覆盖为其他策略。

设置 `PLAYER_MEDIA_DELIVERY=proxy` 并重启应用可恢复全部中转。此设置是兼容回退，不解决小带宽的容量限制。

## 验证记录（2026-10-13）

使用已有片库的两个视频进行了小流量探测，并通过用户扫码完成本地 TV 认证：

| 路径 | 实测结果 |
| --- | --- |
| 网页源不携带 Cookie | MP4 返回 403，HLS 返回 403/412 |
| 网页源携带 Cookie | MP4 返回 206，HLS 清单返回 200 |
| TV MP4 携带站点 Referer | 返回 403 |
| TV MP4 不带 Referer | 返回 206，支持 Range；在测试域名来源下有匹配的 CORS 响应 |
| TV HLS 不带 Referer | 清单与 TS 可请求，但没有 CORS，不能直接交给 hls.js |
| TV 原文件下载 | 返回 206，本次样本为 Matroska；电脑浏览器可出画面 |

浏览器验证使用隔离测试页面模拟 `https://linlunji.cn` 来源，没有修改线上站点。3840×2160 的 TV MP4 在禁止 Referer 后连续出帧，拖到 120 秒后继续推进至 124 秒。首次只设置 302 策略时，后续请求失败；页面策略补齐后通过。

这些是短时、单机样本验证，不代表所有片源、不同网络出口、长时间播放、令牌过期重取或 iPhone 真机已通过。原文件出画面也不代表全部音轨兼容。上线后应至少检查实际 ECS 签发地址、用户网络下播放与拖动、视频请求是否落在网盘域名，以及 ECS 出口是否不再随直连播放持续增长。

### 生产补充验证

生产扫码曾返回 `TV_PLAYBACK_ERROR / 设备数超限`。用户退出本次本地测试设备后，生产 TV 认证成功，页面显示“已认证”，无需再次占用本地 TV 设备名额。

随后发现同一剧集含“杜比视界渐进式直连”和“普通 4K HLS 中转”：旧选择逻辑默认选择超高清中转，且直连返回 `206 video/x-matroska`、无 ACAO，被页面固定的 `crossorigin="anonymous"` 拦截。生产页面临时原生播放器移除该属性后，实际从 `video-play-p-zb.drive.quark.cn` 收到 206，3840×2160 连续解码超过一分钟；拖到 120 秒后推进到 123.33 秒，`readyState=4`。临时播放器随后移除，未直接修改生产部署。

该验证说明原生渐进式视频不必要求 CORS，不能把 hls.js / Web Audio 的跨域要求套用到所有视频播放。这一轮验证针对渐进式直连，未验证 iPhone。

### iPhone 后续反馈与验证边界

用户刷新后，iPhone Safari 已显示新版直连与兼容按钮，但仍在首播阶段中断。因此此前的电脑直连成功不能视为手机验收通过。实现现增加原生 HLS 分流，避免默认使用杜比 MKV；对应能力传递、302 不转发媒体、旧客户端回退、显式中转与源刷新已覆盖测试。由于本轮授权浏览器调试接口不可用，尚未采集失败手机的真实媒体错误，也尚未完成这条原生 HLS 路径的真机实测，不应宣称已确认唯一根因或已解决所有 iPhone 播放问题。
